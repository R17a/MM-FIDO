# Meshtastic-FIDO: справочник по config.json

`config.json` — обычный JSON без комментариев. Программа перезаписывает файл целиком при
каждом сохранении настроек (смена темы F8, пересканирование F5, правка подписей F3 и т.п.),
поэтому вписанные прямо в него комментарии были бы стёрты — справочник вынесен отдельным
файлом.

Большинство ключей выставляется **мастером первичной настройки**. Мастер появляется только
на самом первом запуске (когда в `config.json` ещё нет языка) и сам больше не открывается —
это одноразовый экран с полями имени, языка, устройства и глубины истории
(`replication_period`). Чтобы поменять любой заданный там ключ позже — правь
`config.json` вручную **при закрытой программе** (при работающей программе правка будет
затёрта при первом же сохранении настроек).

## Все ключи одним списком

«По умолчанию» = поведение, когда ключа в `config.json` нет вовсе. Почти у всех ключей
есть рабочее значение по умолчанию — файл можно вести минимальным: ключи, чьё значение
совпадает с «по умолчанию», можно из файла удалить, поведение не изменится. Единственный
ключ без значения по умолчанию — `language`: без него на старте запускается мастер
первичной настройки. Подробности и оговорки по каждому ключу — в разделах ниже.

**Часть ключей программа дописывает обратно сама** — их удаление из вручную
«подчищенного» файла временно:
- `mock_mode`, `device`, `mock_role`, `mock_has_internet` — при каждом успешном
  подключении к реальной плате (сохраняется фактически обнаруженные роль/NodeID, чтобы
  на диске отражалась реальность, а не дефолт мастера);
- `theme` — при переключении F8; `tree_mode` — при переключении F4; `taglines` — при
  правке в F3; `terms_accepted` — на экране «Политика сети»; `country` — при автозаполнении
  из частотного региона платы.
Всё остальное программа сама не трогает.

## Личные данные / интерфейс

- `language` — код языка интерфейса (`ru`/`en`/`zh`), выставляется мастером настройки.
- `tree_mode` — F4/Ctrl+T, показывать дерево ответов по умолчанию вместо плоского списка.
- `theme` — `textual-light`/`textual-dark`, переключается F8.
- `first_name` / `last_name` — имя автора, идёт в `From` каждого отправленного письма.
- `taglines` — список подписей (tagline), редактируется в F3; один элемент — всегда
  используется, несколько — случайный выбор при каждой отправке нового письма/ответа;
  пустой список — подпись не добавляется.

## Подключение к плате

- `mock_mode` — `true` = MOCK-режим (работа без физической платы, для ознакомления);
  `false` / нет ключа = подключаться к реальной плате. Выбирается в мастере; сменить
  потом — вручную здесь либо пройти мастер заново (удалив `config.json`).
- `connection_type` — `serial`/`ble`/`tcp`, каким транспортом подключаться к плате
  (USB / Bluetooth / локальная сеть). От него зависит, какой из двух ключей ниже нужен.
- `ble_address` — используется **только при `connection_type: "ble"`**. MAC-адрес
  конкретной BLE-платы (пусто — подключаться к первой найденной).
- `tcp_host` — используется **только при `connection_type: "tcp"`**, то есть при
  подключении к плате по Wi-Fi/локальной сети. IP или hostname платы (порт 4403, если не
  указан другой в виде `хост:порт`). При USB/BLE-подключении ключ не нужен и в `config.json`
  не появляется. К интернет-синхронизации (DHT/Relay/MQTT) отношения не имеет — та работает
  через сеть самого компьютера.

## Диагностика / радио

- `log_level` — `DEBUG`/`INFO`/`WARNING` и т.п. На `DEBUG` имя лог-файла в `Logs/` становится
  говорящим — несёт режим пейсинга и признак интернет-синхронизации; на остальных уровнях
  имя фиксированное (`mm-fido.log`). **Это единственный ключ, влияющий на имя лог-файла** —
  если лог называется непонятно, смотри сюда первым делом.
  Расшифровка суффиксов имени: `internet_` в начале — был включён `internet_sync_enabled`;
  `auto` — `radio_fragment_pacing` не задан или `"auto"` (какой режим он выбрал в рантайме —
  в теле лога, строка «пейсинг auto → …»); `sequential_A` / `sequential_B` — явный
  `sequential` с `radio_sequential_window_enabled` `false`/`true`; `batch` — явный `batch`.
- `radio_watchdog_enabled` — диагностика и автовосстановление зависшего интерфейса платы;
  по умолчанию выключен, включается вручную на время полевых тестов. Если сам процесс
  переподключения зависает надолго (около 6 минут) без ответа — программа завершается с
  кодом `90`, рассчитывая на перезапуск внешним лаунчером (на Linux `run.sh` перезапускает
  по этому коду автоматически).

## Радио: пейсинг фрагментов и батч-синхронизация (полигон для полевых тестов)

- `radio_fragment_pacing` — `"auto"` (по умолчанию), `"batch"` или `"sequential"`:
  слать/подтверждать весь раунд фрагментов сразу или ждать подтверждение на каждый
  фрагмент по одному.
  - **`auto`** — режим выбирается сам на каждую отправку: **есть работающий MQTT** (мост
    на связи с брокером, каждый фрагмент быстро закрывается подтверждением) → `batch`;
    **только LoRa** → `sequential` по одному фрагменту без окна. Это то, что нужно почти
    всегда: `batch` по чистому LoRa на большом объёме почты топит канал и плату.
  - `batch` / `sequential` заданные явно — принудительный override (для полевых A/B-тестов).
- `radio_sequential_window_enabled` — только при явном `radio_fragment_pacing="sequential"`:
  `false` (по умолчанию) — строго один фрагмент в полёте (`sequential_A`), `true` —
  несколько одновременно в окне (`sequential_B`). Авто-режим окно НЕ включает.
- **Ручной выбор (если не `auto`):**
  - `batch` — когда платы заведомо рядом, сигнал сильный И есть MQTT: меньше всего
    обменов. На плохом канале / без MQTT залповый режим теряет больше.
  - `sequential` (окно `false`) — по одному фрагменту: максимальная устойчивость на
    слабом/загруженном канале, но медленнее.
  - Обе стороны могут стоять на разных режимах — это не мешает обмену (см. «Совместимость» ниже).
- `radio_batch_sync_enabled` — один запрос синхронизации на ВСЕ ещё не опрошенные эхи раунда
  вместо одного на эху (батч-разведка); по умолчанию `false`.
- **Совместимость режимов.** `radio_fragment_pacing` и `radio_sequential_window_enabled` —
  чисто отправительские настройки (порядок и темп выкладывания фрагментов кадра в эфир).
  В формат кадра пейсинг не входит, с собеседником не согласуется, фрагментация и поведение
  приёмника от него не зависят; подтверждения — транспортные (платы / MQTT), не наши. Ключи
  читаются из СВОЕГО `config.json` при каждой отправке. → Узлы с разными режимами
  (`batch` / `sequential_A` / `sequential_B`) свободно обмениваются почтой, в т.ч. по-разному
  в каждую сторону (`A→B` batch, `B→A` sequential). Застрявший фрагмент в любом режиме
  добирается общим повторным запросом.
- `radio_mtu_bytes` — размер кадра внутреннего протокола упаковки, по умолчанию `200`;
  единый и для LoRa, и для MQTT-моста (одна фрагментация на оба транспорта). Меньше
  значение = больше фрагментов на кадр, но каждый фрагмент меньше — рычаг для MQTT-only
  «городского» сценария, где вероятность потери хотя бы одного фрагмента из залпа растёт с
  их числом.

## Глубина реплицируемой истории

- `replication_period` — сколько истории эхоконференций тянуть на этот узел:
  `"all"` (без ограничения), `"year"`, `"month"`, `"week"` (по умолчанию), `"day"`.
  **Это СКОЛЬЗЯЩЕЕ окно:** граница «сейчас − период» пересчитывается на каждом обмене и
  движется вперёд вместе с часами. Выбрал «За месяц» — узел всегда получает последние
  30 дней; новая почта приходит как обычно (она всегда внутри окна в момент публикации),
  отсекается только история старше периода. Это ДРУГАЯ ось, чем инкрементальный докач
  «всё, что после последнего известного».
  **Действует ТОЛЬКО когда у узла нет выхода в интернет.** У узла с интернетом окно не
  ставится — пропускная способность не проблема, а если это `CLIENT_BASE`, его клиенты иначе
  недополучат историю, которую сам узел себе урезал. Поиск через интернет (DHT/Relay) окно
  тоже не применяет никогда. **Личная почта (NETMAIL) под ограничение не попадает** — она не
  «протухает». Уже сохранённые локально сообщения не удаляются — расширил период, следующий
  обмен дотянет остальное.
  **Как задаётся:** ТОЛЬКО в мастере первичной настройки — выпадающий список «Глубина
  истории эхоконференций» (варианты «Всё целиком» → `all` по умолчанию, «За год» → `year`,
  «За месяц» → `month`, «За день» → `day`). Мастер повторно не открывается — поменять период
  после первого запуска можно лишь вручную: править `config.json` при закрытой программе.

## Гео-фильтр каталога эхоконференций

- `echo_regions` — список `"СТРАНА"` или `"СТРАНА.РЕГИОН"`, напр. `["RU.MSK", "RU.SPB"]`.
  Отвечающий хаб отдаёт только **глобальные эхи + попавшие под фильтр**. Экономит LoRa-канал:
  не гнать сотни имён эх других городов/стран.
  - Глобальные эхи (`SYS.*`, `EN.TALK`, `RU.TALK` — язык, не гео) — всегда в ответе.
  - Эха уровня страны — если её `СТРАНА` есть в любом элементе `echo_regions`.
  - Эха уровня региона — если её `СТРАНА.РЕГИОН` точно указана в `echo_regions`.
  - Гео эхи именуются `<СТРАНА>.<РЕГИОН>.<ТЕМА>` (`RU.MSK.TALK`); принадлежность
    определяется по имени.
  - **Действует ТОЛЬКО когда у узла нет интернета** (тот же критерий, что
    `replication_period`). Узел/хаб с интернетом несёт и отдаёт ВЕСЬ каталог.
  - `[]` (мастер пройден, регионов не указано — так пишет мастер всегда) → только
    глобальные эхи. Ключа нет вовсе (старый конфиг) → фильтр не применяется, полный список
    как раньше.
  - К `echo_regions` из конфига опрос почты автоматически добавляет регионы всех локально
    подписанных региональных эх — на что подписан, то и синхронизируется, даже если регион
    в конфиг руками не вписан.
  - Диалог Subscribe (`S`) выбирает Страна → Регион по «оглавлению» хаба и подписывает
    отмеченные эхи (два коротких запроса вместо полного списка — экономия LoRa).
  **Как задаётся:** мастер первичной настройки этот ключ больше НЕ спрашивает (пишет
  всегда `[]`) — регион выбирается в диалоге Subscribe (`S`). Явно перечислить регионы
  можно вручную в `config.json` при закрытой программе.

## Скрытые из списка эхоконференции

- `hidden_areas` — список EchoID, которые узел кэширует и реплицирует как обычно, но
  оператор НЕ хочет видеть в списке на главном экране. Актуально для инфраструктурного узла
  (`CLIENT_BASE`/`ROUTER`): он полной репликацией каталога и гео-каталогом затягивает у себя
  не только свои подписки, но и чужие эхи — список замусоривается.
  - Формат элемента: точный EchoID (`"DE.BER.MEET"`) или хвостовой шаблон
    (`"DE.*"` — все эхи страны DE, `"TEST.*"` — вся тема TEST). Регистр не важен.
  - **Чисто визуальный фильтр.** Скрытые эхи по-прежнему принимаются, реплицируются в обе
    стороны и отдаются другим узлам в каталоге — узел остаётся полноценным зеркалом. Фильтр
    действует только в интерфейсе: список эх на главном экране, поэховый обход `R` («читать
    всё новое») и `Space` («след. непрочитанное»), выбор эхи для форварда.
  - **Работает только на инфраструктурном узле** — роль `CLIENT_BASE` / `ROUTER` /
    `ROUTER_LATE` / `ROUTER_CLIENT`. У обычного `CLIENT` ключ игнорируется, эхи в списке
    всегда показываются (у него там и так только его собственные подписки). Сменилась роль
    на клиентскую — скрытые эхи снова появляются.
  - `SYS.ANNOUNCE` и `NETMAIL` скрыть нельзя (служебные). Одинокая `"*"` игнорируется —
    опечатка не должна спрятать весь список.
  - Ключа нет / пустой список → ничего не скрыто (прежнее поведение).
  - Чтобы совсем перестать хранить эху — это отписка (`D`), а не `hidden_areas` (но на
    `CLIENT_BASE` с полным каталогом эха заведётся снова — там и нужен именно этот фильтр).
    Правится вручную в `config.json`, шага мастера нет (на первом запуске скрывать ещё
    нечего).

- `hub_hide_cached_areas` — `true` по умолчанию. Отдельно от `hidden_areas` (списка
  вручную): на инфраструктурном узле эхи, которые появились НЕ по подписке оператора, а
  полной репликацией каталога или автосозданием по входящему письму, скрыты из списка
  сразу, без перечисления. Поставить `false`, чтобы их увидеть — например, при отладке,
  чтобы убедиться, что узел действительно кэширует чужие эхи. На обычном `CLIENT` не
  действует (там и так только свои подписки). Приём, репликация и отдача в каталоге от
  флага не зависят.

## Оповещения

- `new_mail_announce_enabled` — по умолчанию `true`. Когда в эхоконференции появилась новая
  почта (написана пользователем или пришла пушем от соседа), узел через несколько секунд
  шлёт ОДНО короткое служебное оповещение со списком таких эх — чтобы соседи подошли
  синхронизироваться, не дожидаясь своего планового опроса. `false` — оповещение не шлётся
  (сама почта и синхронизация работают как обычно). Личной почты (NETMAIL) не касается —
  она доставляется адресно.

## DHT/Relay (интернет)

DHT/Relay — путь поиска собеседника через интернет, независимый от LoRa и MQTT. Состоит из
двух механизмов: DHT-рандеву с попыткой прямого соединения и отдельно Relay (сервер-
посредник) со своим списком узлов. Ключи ниже позволяют управлять ими по отдельности — все
по умолчанию `true` (сначала DHT, Relay — последняя попытка, если DHT не дал прогресса).

- `internet_sync_enabled` — общий рубильник DHT/Relay ЦЕЛИКОМ (и исходящие попытки, и приём
  чужих подключений через релей). `false` — узел работает только по LoRa/MQTT.
  Как часто пробовать DHT/Relay отдельным ключом больше не задаётся: теперь Слой 2
  запускается в конце каждого цикла опроса почты (раз в 60 с). Прежний ключ
  `internet_sync_interval_connected_sec` больше не читается — если он остался в старом
  `config.json`, его можно удалить, он ни на что не влияет.
- `internet_direct_dht_enabled` — по умолчанию `true`. `false` — полностью пропускает DHT и
  попытки прямого соединения, сразу переходит к Relay. Для изолированной проверки ИМЕННО
  Relay без DHT.
- `internet_direct_relay_enabled` — по умолчанию `true`. `false` — Relay не пробуется вообще,
  даже если DHT не нашёл ничего полезного (цикл просто завершается без прогресса). Для
  изолированной проверки ИМЕННО DHT.
- `lan_discovery_enabled` — по умолчанию `true`. Третий, независимый от DHT/Relay путь
  обнаружения — постоянный фоновый UDP-broadcast в пределах одной локальной сети, без
  интернета и без DHT-роя. `false` — для изолированной проверки ИМЕННО DHT/Relay без LAN.
  Работает только в одном broadcast-домене (без VLAN-маршрутизации не пройдёт). Подчинён
  общему `internet_sync_enabled`.
- `upnp_port_mapping_enabled` — по умолчанию `true`. Автопроброс TCP-порта узла (9999) через
  UPnP — снимает ручную настройку роутера для прямого DHT-соединения, тот же протокол,
  которым торрент-клиенты автоматически открывают себе порт. Только для инфраструктурных
  ролей (пробрасывать порт имеет смысл, только если на нём что-то слушает). Best-effort:
  если UPnP на роутере выключен/не поддерживается — тихо ничего не делает. `false` — не
  пытаться вообще (например, если роутер требует ручного подтверждения UPnP-запросов).

Адрес релей-сервера отдельным ключом не задаётся — он зашит в программу. К какому узлу
подключаться через релей, узел выясняет сам (спрашивает у релея, кто на нём сейчас
зарегистрирован). Включить/выключить сам путь через релей — `internet_direct_relay_enabled`
выше (или общий `internet_sync_enabled`).

## MQTT-мост

- `mqtt_bridge_enabled` — по умолчанию `true`. Килсвитч моста целиком, независимо от настроек
  MQTT-модуля самой платы — для полевых тестов DHT/Relay, где нужно изолировать «нет LoRa и
  нет MQTT, есть только DHT/Relay» без похода в приложение Meshtastic на каждом устройстве.
- `mqtt_channel_filter_enabled` — по умолчанию `false`; `true` включает форвардинг на плату
  и логирование только трафика тех каналов, что реально настроены на этой плате (не весь
  региональный брокер целиком).
- `mqtt_direct_channel_bridge_enabled` — по умолчанию `true`. Килсвитч прямого моста
  обычных каналов между двумя городами через общий MQTT-топик. `false` — мост каналов не
  поднимается; обмен FIDO-почтой по MQTT-топику «Meshtastic-FIDO» это не затрагивает.
- `mqtt_keepalive_seconds` — по умолчанию `60` (известно рабочее значение). Ключ существует,
  чтобы тестировать промежуточные значения (45/30) без правки кода. Меньшие значения на
  Windows однажды совпали с обвалом приёма (входящие сообщения в ноль, не восстанавливается)
  — если приём по MQTT пропал и не возвращается, верни `60`.
- `mqtt_outgoing_publish_pace_seconds` — по умолчанию `0.2`. Пауза между публикациями
  последовательных фрагментов ОДНОГО кадра канала «Meshtastic-FIDO». Без неё фрагменты
  уходили в MQTT залпом без зазора — на нестабильном пути (сотовый хотспот) все, кроме
  первого, стабильно терялись. Это тайминговая задержка, а не таймаут подтверждения.

## Сетевая телеметрия

Необязательные ключи. НЕ влияют на работу узла — только на сводную статистику сети
(сколько узлов и откуда), которую ведёт сервер-релей и показывает сайт проекта.

- `country` — код страны ISO-2 (`"RU"`, `"DE"`, `"US"`). Заполняется автоматически при
  первом подключении к плате, если её частотный регион однозначно соответствует стране.
  Задавать вручную стоит, только когда автоопределение по IP ошибётся (узел за VPN/на VPS)
  или регион платы шире страны.
- `firmware` — тип прошивки узла: `"meshtastic"` (по умолчанию) или `"meshcore"`. Пока
  поддержана только Meshtastic, ключ заведён заранее.
